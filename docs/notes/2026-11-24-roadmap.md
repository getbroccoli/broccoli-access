# Roadmap decisions (2026-11-24)

Scope is in [the product requirements](../prd.md). This note keeps the reasons, from the brainstorm with the product owner.

## The integration user

- **Why:** an app that dislikes automation blocks the user that did it. With the owner's own session, that is the owner. With an integration user, the damage stops at a user nobody works as. It also works when the owner is away.
- **It does not make automation allowed.** Almost every app's terms forbid automated use in any form. A robot in a browser breaks them as much as a call to the internal API does. The notice before connecting stays.
- **A Google Workspace user**, because it then has a mailbox for the codes apps send, and "Sign in with Google" for many apps.
- **broccoli-access creates it**, as another product in this market does. That needs Google write access, asked for at that moment and not at setup.
- **Two ways to connect, chosen in the Connect dialog.** The integration user, recommended: the owner invites it as an admin in the app, and broccoli-access signs in by itself. Or the owner's own session, handed over by the extension, as in circle 2. An earlier design had the owner sign in as the integration user in Chrome; it asked too much of them.
- **Nobody signs in as it but broccoli-access.** The owner never sees its password.
- **Open:** broccoli-access must set up the integration user's two-step sign-in in Google by itself. Not tested yet.
- **One place holds much.** The instance keeps the integration user's password, and later its two-step secret and mailbox. Suspending the integration user in Google stops all of it at once.

## Server sign-in, tested on 2026-11-24

One test user of our own test domain, a Chromium on our server that reports itself as automated, nothing hidden, a few runs.

- **Google let it sign in**, with email and password, on every run. The test user has no two-step sign-in.
- **Gmail opens** in that browser, so a code or an invitation can be read there with no mailbox permission.
- **Slack's sign-in by email code shows a reCAPTCHA** as soon as the email is typed. broccoli-access stops there.
- **Slack's "Sign in with Google" works**, with no check. Slack then lists the workspaces the user is invited to, with Join, so Slack needs no mailbox at all.

So a connector signs in with Google first, and uses the mailbox only where an app has no Google sign-in. Not tested: two-step sign-in, joining the workspace, Slack's admin calls with that session, and many sign-ins over days.

## Methods

Three agents read the public documents of 21 apps on 2026-11-24. Nothing was tested against a live app.

- **The official API is enough (9):** Linear, GitHub, Atlassian, Asana, Calendly, Dropbox, HubSpot, Zoom, Claude Console. Another product in this market uses a robot for several of them anyway.
- **The internal API works after sign-in (4, and 2 leaning):** Slack, Notion, Figma, ChatGPT; Zapier and Miro lean the same way.
- **A browser is better (2, and 1 guess):** Claude Team and Xero tie the session to a real browser. Canva is a guess.
- **Unknown (4):** Loom, Docusign, Salesforce, 1Password.

So:

- The order is official API, internal API, robot. The robot is the last choice.
- The hard part is signing in, not the actions. Slack and Claude have no password, only a code or link by email. Others send a code to a new device. That is why the integration user needs a mailbox.
- Role change is the usual gap in official APIs (Asana, Calendly).

## Templates

- **No conditions.** A template is a named list, and the owner assigns it. An earlier prototype of ours matched people with a rule language and repaired accounts on a schedule; neither is taken.
- **Several per person**, so "Everyone" plus "Engineer" works without a template per combination.
- **broccoli-access finds differences and a person fixes them**, in all three cases: an app added to a template, an app or a template taken away, and an account changed in the app by hand. One wrong edit of a template would otherwise change many real accounts with nobody looking.
- **Role conflicts:** two templates that give one app different roles show a conflict, and the owner picks. Roles differ per app, so none is "higher".
- **Creating the Google account** is Google Workspace as the first line of the person's list.

## Offboarding

- **It suspends the Google account too**, with the write access creating accounts already needs.
- **On the click**, not on a date: there is no HR system to give the date, and a run with nobody there needs server sign-in.
- **Disable first, Remove after.** Disable can be undone. Remove frees the seat and cannot.
- **No text per app on Remove.** The confirmation says only that it cannot be undone. What each app does with a removed person's data would be a text to maintain for every app.

## Accounts without a person

- **External people are not people in broccoli-access.** Its people come from the directory. A second source, made by hand, needs its own joining and leaving.

## Left out

- **Cost**, from the prototype of 2026-11-20: paying for suspended accounts, unused paid seats, several apps for one job, the approved apps list by kind of work, cheaper replacements, and the size map.
- **Access reviews**, postponed.

## The connector factory

- **Why:** with 30 apps, the product owner approving each fake API, creating each workspace and running each real check makes them the bottleneck 30 times.
- **Its own Google Workspace**, a test domain, which agents use in full: they create the test people, sign up to apps with "Sign in with Google", and read the test mailboxes for codes and invitations. The real company domain is never used.
- **Its own store for secrets**, which agents read and write, one item per app and secret.
- **Parked:** when an app needs a person, for a payment, a CAPTCHA or a phone check, the agent writes down what is needed and takes the next app. The agents' rules are the product's: never get around a check.
- **Trials end.** Each app's report names the cheapest plan that allows the actions for good. Agents never make trial after trial.
- **A fake app is approved by evidence**: the connector's calls to the real app match its calls to the fake. The product owner reads one report per app at the end and can reject it.
- **The product owner's gates stay** for the connector contract and the data model.
- **The list of 30 is the product owner's gate too.** An agent researches it; no app is investigated before they approve the list.
- **The states of an app:** listed, investigated, workspace ready, explored, built, checked, live, maintained. A failed weekly check sends it back to explored.

## Order

- **Two circles, not four.** Agents build the parts next to each other, so small circles matter less. Circle 3 holds everything we know how to build, in three ordered parts. Circle 4 holds robots, which nobody has proven yet; planning them now would mean planning them twice. Server sign-in moved into circle 3 after the test above.
- **Part 1 first**, because it removes the worry about blocked owners and gives part 2 its actions. Part 3 needs the templates of part 2.
- **The cost:** the data model, the fake APIs and the screens of all of circle 3 are approved before its first task.
- **The connector factory is in neither circle.** It is not the product, it never ends, and a parked app must not hold a release. Circle 3 is done with Slack and Linear; circle 4 waits for what the factory learns about the apps that need a robot.
